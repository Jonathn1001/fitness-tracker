How They Talk

Two programs, one shared script. Verbs, addresses, forms — and what happens when someone goes off-script.

Radio discipline

Pilots and air traffic control do not chat. They use fixed phrases in a fixed order, because a misheard sentence at 300 knots is fatal. Every message names who it is for, what is wanted, and nothing else.

Two programs talking over the internet follow the same discipline. Every request carries a verb (what kind of thing this is) and an address (what it concerns).

GET /sessions "Send me the list of workouts." Asks for data, changes nothing.
POST /sessions "Create a new workout." The verb for make something that did not exist.
PATCH /sessions/:id "Change part of this one workout." The :id is a blank filled in with a specific workout.
DELETE /sessions/:id/sets/:setId "Remove that one set from that one workout." Addresses nest, like folders.

GET is safe to repeat. POST is not — repeat it and you get two workouts. Half the tricky bugs in this app come from that one asymmetry.

The entry form, in full

That "form accepted" step is a real file. Six lines describe every request allowed to start a workout.

CODE 

export class CreateSessionDto {
  @IsOptional() @IsUUID() templateDayId?: string;
  @IsDateString() date: string;
  @IsOptional() @IsEnum(['walk', 'run']) warmupType?: 'walk' | 'run';
  @IsOptional() @IsInt() @Min(1) warmupDurationMin?: number;
  @IsOptional() @IsString() notes?: string;
  @IsUUID() idempotencyKey: string;
}
PLAIN ENGLISH

"Any request that wants to create a workout must look exactly like this."

You may leave out the planned day — but if you send one, it has to be a real UUID, not the word "monday".

The date is required and must be a real date. "yesterday" is rejected here, before it can poison a chart six months from now.

Warmup type may only be walk or run. This is the list the whole app agrees on — send "treadmill" and the request never reaches the rules.

If you send a duration it must be a whole number of at least 1. No negative warmups, no half minutes.

Notes can be any text, or nothing.

The ticket number is required and must be a UUID. Module 5 is built on this line.

💡
Key insight — validate at the border

Bad data is cheapest to stop at the front door. Once it is in the database, every screen, every chart and every AI review has to cope with it forever. Engineers call this validation at the boundary, and it is one of the highest-value things you can ask an AI assistant to add.

The phone's memory

The app does not re-ask the server every time you glance at a screen. It keeps answers for a while — and the whole caching policy is three lines.

CODE 

export function useSessions(params?: {
  // ...
}) {
  return useQuery({
    queryKey: ['sessions', params],
    queryFn: () => listSessions(params),
  })
}
PLAIN ENGLISH

"Any screen that needs the workout list should ask me, not the network."

The filters — date range, page number — come in as options.

Hand the work to React Query, which handles the remembering.

This is the label on the drawer: "sessions, with these filters". Same label → same cached answer. Different filters → different drawer.

And this is what to do when the drawer is empty: actually call the server.

Elsewhere in the app the answer is kept fresh for five minutes before it is re-checked.

⚠️
The bug this creates

"I saved it but it does not show up" is almost always a cache that was not thrown away after a write. If you ever report that symptom to an AI assistant, say "invalidate the query after the mutation" — that is the exact fix, and naming it saves you three wrong guesses.

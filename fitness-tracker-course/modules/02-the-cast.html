The Cast

Every file in this project has exactly one job. Learn the job titles and the codebase stops looking like a pile.

A film crew, not a one-man band

On a film set nobody does everything. The camera operator does not write dialogue; the editor never touches a light. The crew is specialised, and that is why a scene can be re-shot without rebuilding the whole production.

This codebase is organised the same way. Each of the roles below appears over and over, in every feature.

🎬
Controller — the receptionist

Takes the incoming request, checks the caller is logged in, and hands it to the right specialist. Contains no thinking of its own.

🧠
Service — where the rules live

"You cannot log a warmup on a kickboxing day." "One AI review per day." All the real decisions happen here.

📋
DTO — the entry form

A written description of what an incoming request is allowed to contain. Anything that does not match is rejected before it reaches the rules.

🗄️
Prisma — the archivist

The only part of the backend allowed to touch the database. Everything else asks it politely.

The receptionist, in real code

Here is the actual function that handles "start a new workout". Notice how little it does.

CODE 

@Controller('sessions')
@UseGuards(JwtAuthGuard)
export class SessionsController {
  // ...
  @Post()
  create(@CurrentUser() u: { id: string }, @Body() dto: CreateSessionDto) {
    return this.sessionsService.create(u.id, dto);
  }
PLAIN ENGLISH

"Everything in this file answers requests whose address starts with /sessions."

"And nobody gets past this door without a valid pass." This is a guard: one line, applied to every function below it, so you cannot forget it on one of them.

The receptionist's name badge.

"This next function handles POST — the verb browsers use for create something new."

Two things get handed in: who is asking (pulled from their pass, never from the request body — that would let anyone claim to be anyone) and what they sent.

And then it immediately delegates. That is the whole job. A receptionist who starts making medical decisions is a bug.

💡
Key insight — separation of concerns

Thin receptionist, thick specialist. When rules live in services instead of controllers, the same rule can be reused by three different doors — and tested without pretending to be a web browser.

Where everything lives

Two folders, two casts. You will spend most of your time in one of these eight places.

backend/src/ The program running on the rented server
auth/ Signup, login, passes and refreshes
sessions/ Workouts, sets and rounds — the heart of the app
templates/ Your weekly plan: which day is gym, which is kickboxing
feedback/ Talks to Google's Gemini and stores the review
frontend/src/ The program running on your phone
pages/ One file per screen: Dashboard, History, Progress, Session…
hooks/ Reusable "fetch this and keep it fresh" logic
api/ The list of every request the phone knows how to send
store/ The few facts every screen needs at once, like who is logged in

One rule, one home

Sessions, sets and rounds all need the same check: is this workout actually yours? It used to be written three times. Now it is written once, and the comment above it explains why that matters more than tidiness.

CODE 

export async function assertSessionOwned(
  prisma: PrismaService,
  userId: string,
  sessionId: string,
) {
  const session = await prisma.session.findUnique({ where: { id: sessionId } });
  if (!session || session.userId !== userId) throw new NotFoundException();
  return session;
}
PLAIN ENGLISH

"Insist that this workout belongs to this person." The name is a sentence — good names save you reading the body.

It needs the archivist, the person asking, and the workout in question.

Go and fetch that one workout by its id.

If it does not exist or it belongs to somebody else — same answer: "not found."

Notice it does not say "forbidden". "Forbidden" would quietly confirm the workout exists, letting a stranger map out other people's data by guessing ids. "Not found" tells them nothing.

Otherwise, hand back the workout so the caller does not have to fetch it twice.

⚠️
The mistake this prevents

When the same security check is copy-pasted into three files, someone eventually fixes a bug in one copy. The other two keep shipping. A rule with three homes is a rule with two exploits.

The phone-side cast

The frontend has its own division of labour. This is the entire "who is logged in" store — small on purpose.

CODE 

// Access token is kept in memory only. On page reload the refresh-token
// HTTP-only cookie is used to re-issue an access token via /auth/refresh.
export const useAuthStore = create<AuthStore>()((set) => ({
  accessToken: null,
  setToken: (token) => set({ accessToken: token }),
  clearToken: () => set({ accessToken: null }),
}))
PLAIN ENGLISH

The comment is doing real work: it explains a deliberate choice, not what the code says. Keep the pass in memory only — never written to disk.

Why? Anything written to phone storage can be read by other scripts on the page. Losing it on refresh is the price; module 4 shows how the app recovers.

Create a shared box that every screen can read from and write to.

It starts empty — nobody is logged in when the app opens.

Two things you can do to it: put a pass in…

…or throw the pass away, which is what logging out means on this side.

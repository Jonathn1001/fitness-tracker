One Tap, Many Moving Parts

You tap "finish". Six pieces of software wake up. Here is the whole relay, end to end.

First — what is this thing?

It is a workout journal you install on your phone — technically a PWA. You log gym sets and kickboxing rounds, and an AI writes you a training review every couple of weeks.

💪
Gym logging

Every set you do: which exercise, how many reps, how much weight.

🥊
Kickboxing rounds

Each round gets a quality score from 1 to 5, so bad days are visible later.

🤖
AI training review

Your last 14 days get sent to Google's Gemini model, which writes back a coach-style summary.

📶
Works in a basement gym

No signal? Your sets are saved on the phone and sent up the moment the bars come back.

The relay race

Think of your tap as a baton in a relay. Each runner carries it a short distance and hands it to the next — nobody runs the whole track. Software is built the same way, and for the same reason: each runner can be swapped out without retraining the team.

💡
Why anyone should care

When something breaks, the useful question is never "the app is broken" — it is "which runner dropped the baton?" Knowing the legs of the race is what turns a vague bug report into a fixable one.

Two programs, not one

The single most useful thing to understand about this app: it is two separate programs that talk over the internet through an API. They are written in different folders, deployed to different companies, and either can be replaced without touching the other.

📱

frontend/

Runs on your phone. Draws buttons, reacts to taps. Anyone can read this code — it is downloaded to the device. Hosted on GitHub Pages.

⚙️

backend/

Runs on a rented computer at Render. Holds the rules, the passwords, the AI key. Nobody can read this code from outside.

🗄️

Neon Postgres

A database in a third place again. It remembers everything after the phone is closed and the server restarts.

🔑
Say this to an AI assistant

"Put that logic in the backend, not the frontend — it must not be visible to the client." That one sentence prevents a whole category of security mistakes, and it only makes sense once you see the split above.

02

The Cast

Every file in this project has exactly one job. Learn the job titles and the codebase stops looking like a pile.

A film crew, not a one-man band

On a film set nobody does everything. The camera operator does not write dialogue; the editor never touches a light. The crew is specialised, and that is why a scene can be re-shot without rebuilding the whole production.

This codebase is organised the same way. Each of the roles below appears over and over, in every feature.

🎬
Controller — the receptionist

Takes the incoming request, checks the caller is logged in, and hands it to the right specialist. Contains no thinking of its own.

🧠
Service — where the rules live

"You cannot log a warmup on a kickboxing day." "One AI review per day." All the real decisions happen here.

📋
DTO — the entry form

A written description of what an incoming request is allowed to contain. Anything that does not match is rejected before it reaches the rules.

🗄️
Prisma — the archivist

The only part of the backend allowed to touch the database. Everything else asks it politely.

Thin receptionist, thick specialist. When rules live in services instead of controllers, the same rule can be reused by three different doors — and tested without pretending to be a web browser.

One rule, one home

Sessions, sets and rounds all need the same check: is this workout actually yours? It used to be written three times. Now it is written once, and the comment above it explains why that matters more than tidiness.

CODE 

export async function assertSessionOwned(
  prisma: PrismaService,
  userId: string,
  sessionId: string,
) {
  const session = await prisma.session.findUnique({ where: { id: sessionId } });
  if (!session || session.userId !== userId) throw new NotFoundException();
  return session;
}
PLAIN ENGLISH

"Insist that this workout belongs to this person." The name is a sentence — good names save you reading the body.

It needs the archivist, the person asking, and the workout in question.

Go and fetch that one workout by its id.

If it does not exist or it belongs to somebody else — same answer: "not found."

Notice it does not say "forbidden". "Forbidden" would quietly confirm the workout exists, letting a stranger map out other people's data by guessing ids. "Not found" tells them nothing.

Otherwise, hand back the workout so the caller does not have to fetch it twice.

⚠️
The mistake this prevents

When the same security check is copy-pasted into three files, someone eventually fixes a bug in one copy. The other two keep shipping. A rule with three homes is a rule with two exploits.

03

How They Talk

Two programs, one shared script. Verbs, addresses, forms — and what happens when someone goes off-script.

Radio discipline

Pilots and air traffic control do not chat. They use fixed phrases in a fixed order, because a misheard sentence at 300 knots is fatal. Every message names who it is for, what is wanted, and nothing else.

Two programs talking over the internet follow the same discipline. Every request carries a verb (what kind of thing this is) and an address (what it concerns).

GET /sessions "Send me the list of workouts." Asks for data, changes nothing.
POST /sessions "Create a new workout." The verb for make something that did not exist.
PATCH /sessions/:id "Change part of this one workout." The :id is a blank filled in with a specific workout.
DELETE /sessions/:id/sets/:setId "Remove that one set from that one workout." Addresses nest, like folders.

GET is safe to repeat. POST is not — repeat it and you get two workouts. Half the tricky bugs in this app come from that one asymmetry.

The entry form, in full

That "form accepted" step is a real file. Six lines describe every request allowed to start a workout.

CODE 

export class CreateSessionDto {
  @IsOptional() @IsUUID() templateDayId?: string;
  @IsDateString() date: string;
  @IsOptional() @IsEnum(['walk', 'run']) warmupType?: 'walk' | 'run';
  @IsOptional() @IsInt() @Min(1) warmupDurationMin?: number;
  @IsOptional() @IsString() notes?: string;
  @IsUUID() idempotencyKey: string;
}
PLAIN ENGLISH

"Any request that wants to create a workout must look exactly like this."

You may leave out the planned day — but if you send one, it has to be a real UUID, not the word "monday".

The date is required and must be a real date. "yesterday" is rejected here, before it can poison a chart six months from now.

Warmup type may only be walk or run. This is the list the whole app agrees on — send "treadmill" and the request never reaches the rules.

If you send a duration it must be a whole number of at least 1. No negative warmups, no half minutes.

Notes can be any text, or nothing.

The ticket number is required and must be a UUID. Module 5 is built on this line.

💡
Key insight — validate at the border

Bad data is cheapest to stop at the front door. Once it is in the database, every screen, every chart and every AI review has to cope with it forever. Engineers call this validation at the boundary, and it is one of the highest-value things you can ask an AI assistant to add.

The phone's memory

The app does not re-ask the server every time you glance at a screen. It keeps answers for a while — and the whole caching policy is three lines.

CODE 

export function useSessions(params?: {
  // ...
}) {
  return useQuery({
    queryKey: ['sessions', params],
    queryFn: () => listSessions(params),
  })
}
PLAIN ENGLISH

"Any screen that needs the workout list should ask me, not the network."

The filters — date range, page number — come in as options.

Hand the work to React Query, which handles the remembering.

This is the label on the drawer: "sessions, with these filters". Same label → same cached answer. Different filters → different drawer.

And this is what to do when the drawer is empty: actually call the server.

Elsewhere in the app the answer is kept fresh for five minutes before it is re-checked.

⚠️
The bug this creates

"I saved it but it does not show up" is almost always a cache that was not thrown away after a write. If you ever report that symptom to an AI assistant, say "invalidate the query after the mutation" — that is the exact fix, and naming it saves you three wrong guesses.

04

Proving Who You Are

A day pass, a membership card, and what the system does when it notices a card has been cloned.

Two pieces of plastic

Think about a real gym. You have a membership card that lasts a year and lives in your wallet. At the desk it gets swapped for a day pass — a flimsy thing that stops working tonight, which you show at every door inside.

This app issues exactly those two things, for exactly the same reason.

🎫

Access token — the day pass

Lives 15 minutes. Attached to every single request. Kept in the phone's memory only, never written to disk.

💳

Refresh token — the membership card

Lives 7 days. Used only to get a new day pass. Stored in an HTTP-only cookie the app's own code cannot read.

💡
Why not one long-lived pass?

Because stolen passes are the normal case, not the exception. A 15-minute pass is worth almost nothing to a thief; a card that lives in a place scripts cannot reach is hard to steal in the first place. Short life plus limited reach — that is the entire design.

Your password is never stored

The database does not contain your password. It contains the result of putting your password through a one-way blender.

CODE 

const hashed = await bcrypt.hash(dto.password, 12);
const user = await this.prisma.user.create({
  data: { email: dto.email, password: hashed, name: dto.name },
});
PLAIN ENGLISH

Run the password through bcrypt, a scrambler that cannot be run backwards.

The 12 is a cost setting: it makes each scramble take a noticeable fraction of a second. Annoying once at login, ruinous for someone trying a billion guesses.

Store the scrambled version. If this database ever leaks, the attacker gets gibberish, not logins.

Checking a login later means scrambling the attempt and comparing the two results — the original is never recovered, by anyone, including this app.

The cloned card

Every time you swap your membership card for a fresh day pass, the old card is destroyed and a new one issued. So if an old, already-destroyed card ever shows up at the desk, exactly one thing is true: someone copied it.

CODE 

if (stored.revoked) {
  // Reuse of a revoked token — likely stolen. Revoke the whole family.
  this.logger.warn(
    `Refresh token reuse detected for user ${payload.sub} (token ${stored.id}). Revoking family.`,
  );
  await this.prisma.refreshToken.updateMany({
    where: { userId: payload.sub, revoked: false },
    data: { revoked: true },
  });
  throw new UnauthorizedException('Refresh token reuse detected');
}
PLAIN ENGLISH

"Someone just presented a card we already destroyed."

The comment states the conclusion, not the mechanics — the honest owner and a thief both hold a copy, and we cannot tell which one is standing here.

Write a warning to the log with the user id and the card id. Note what is not logged: no email, no name, no token value. Logs get shipped to other systems and read by other people.

So destroy every card this user currently holds…

…in one sweep.

And refuse this request. Both the thief and the real owner get logged out; the owner signs in again with their password, which the thief does not have. Momentary annoyance beats a silent intruder.

🔍
This pattern has a name

It is called refresh token rotation with reuse detection. Saying that phrase to an AI assistant gets you this whole design in one shot; asking for "make login secure" gets you a coin flip.

Spot the bug

Below is a login check of the kind that appears in a thousand tutorials. One line makes the entire scheme from the last two screens pointless. Click it.

Find the line that breaks security:

1 const user = await this.prisma.user.findUnique({ where: { email: dto.email } });
2 if (!user) throw new UnauthorizedException('Invalid credentials');
3 const valid = dto.password === user.password;
4 if (!valid) throw new UnauthorizedException('Invalid credentials');
5 return this.issueTokens(user.id, user.email);

The real file uses await bcrypt.compare(dto.password, user.password) — scramble the attempt, compare the scrambles. A plain === only works if the stored password was never scrambled at all, which means the database is holding everyone's real password in plain sight.

Why the app never asks you to log in twice

Your day pass expires every 15 minutes, but you never notice. That is one piece of code doing the swap silently in the background.

1
A request comes back rejected

The server answers 401 — "your pass is no good any more".

2
The app quietly visits the desk

It calls /auth/refresh. The membership card rides along automatically in the cookie — no code has to fetch it.

3
Everyone else waits in line

If five requests fail at once, only one refresh happens. The other four queue up and are handed the new pass. Without that, five refreshes race, four cards get destroyed, and reuse detection logs you out for no reason.

4
The original request is retried

With the fresh pass attached. You saw nothing but a slightly slower save.

5
Unless the card is dead too

Then the pass is thrown away and you land on the login screen — the only time you ever see this machinery.

An attacker steals one of the two credentials. Which one hurts less, and why?

05

When The Signal Dies

Basement gyms have no bars. The app is built so that stops mattering.

The letters in your bag

You write letters all week while travelling. There is no postbox. You do not throw them away and you do not stand in the street waiting — you put them in your bag, and post the lot when you pass a postbox.

That is the entire offline design. Nothing is lost, nothing blocks, and the sending happens later without you thinking about it.

Before this existed, the finish button failed silently underground: the set looked saved, the screen moved on, and the workout was gone. Silent data loss is the worst class of bug there is — nobody reports it, because nobody notices.

Which letters go in the bag?

Not every failed request belongs in a queue. This function is the doorman, and its three refusals are more interesting than its acceptance.

CODE 

export function shouldQueue(error: {
  response?: unknown
  config?: QueueableConfig
}): boolean {
  const config = error.config
  if (!config) return false
  if (error.response) return false
  if (config.__isReplay) return false

  const method = config.method?.toLowerCase()
  return !!method && QUEUEABLE_METHODS.has(method)
}
PLAIN ENGLISH

"Given a request that just failed — does it belong in the bag?"

No description of the request at all? Nothing to replay later. Refuse.

The important one. If the server answered — even to say "that is invalid" — this is not a signal problem. Queueing it would hide a real error from the user and replay a request the server already refused. Refuse.

If this failure came from replaying the bag, do not put it back in the bag. Without this line every drain adds a fresh copy and the queue grows forever.

Finally, look at the verb.

Only POST, PUT, PATCH and DELETE qualify — the verbs that change something. A failed read is not worth saving; the screen can just ask again later.

💡
Key insight — "no answer" and "bad answer" are different failures

Both show up as an error in the code. Treating them the same is how apps end up hiding genuine errors behind a spinner, or endlessly retrying a request the server will never accept. The distinction here is a single line: if (error.response) return false.

Posting the letters

The drain loop is short, and every line of it is a decision someone had to make.

CODE 

const all = await db.getAllFromIndex(STORE, 'queuedAt')

for (const entry of all) {
  let attempts = 0
  let success = false

  while (attempts < 5 && !success) {
    try {
      await sendRequest(entry)
      await db.delete(STORE, entry.id)
      success = true
      emitChange()
    } catch {
      attempts++
      if (attempts < 5) {
        await delay(Math.pow(2, attempts) * 1000)
      }
    }
  }
PLAIN ENGLISH

Fetch every letter, sorted by when it was written. Order matters: replaying "set 3" before "start workout" would fail for a reason that has nothing to do with the network.

Take them one at a time.

Each letter gets its own attempt counter — one stubborn letter must not consume the allowance of the rest.

Try up to five times, stopping early the moment it works.

Send it.

Delete only after the send succeeded. Reverse those two lines and a crash between them destroys the set forever.

Tell the rest of the app the bag changed, so the little "3 pending" badge updates.

If it failed, count the attempt…

…and wait before trying again: 2 seconds, then 4, 8, 16. This is exponential backoff — hammering a struggling server is how you keep it down.

After five failures it gives up, warns in the console and fires an event the UI can show. Loudly, not silently.

Why you do not end up with four identical workouts

Retrying a create is dangerous — that was the module 3 quiz. The fix is the field you saw in module 1: idempotencyKey. The phone generates one random ticket number per workout and reuses it on every retry.

CODE 

const existing = await this.prisma.session.findUnique({
  where: { idempotencyKey: dto.idempotencyKey },
});
if (existing) {
  if (existing.userId !== userId) {
    throw new ConflictException('Idempotency key already in use');
  }
  return existing;
}
PLAIN ENGLISH

Before creating anything: has a workout with this ticket number already been created?

If yes…

…and it belongs to somebody else, refuse. Someone is guessing ticket numbers, or a bug is recycling them.

Otherwise hand back the workout that already exists. The retry gets the same answer as the original, and no second workout appears.

This is what idempotent means, and it is the single most useful word to know when asking an AI assistant to make writes safe to retry.

🔒
One more subtlety

Logging out empties the bag. A queued letter carries no identity of its own, so replaying it after a different account signs in would file your sets against their workout. Two lines of code, one very strange bug prevented.

06

Shipping It

Security lanes, boarding gates, and the meter that runs every time the AI is asked a question.

Nobody boards without clearing security

At an airport you do not walk from the kerb onto the plane. You pass through lanes — document check, bag scan, body scan — and the gate only opens for people who cleared all of them.

Code takes the same route. Every proposed change runs through four lanes — collectively called CI — before it is allowed anywhere near real users.

📏

Lint

House style and obvious mistakes. Cheap, fast, catches the silly things.

🔎

Typecheck

"You promised this was a number and handed it a date." Catches whole categories of bug without running anything.

🧪

Tests

Unit tests check the rules in isolation; e2e tests start a real database and drive the API like a user.

🛡️

Audit

Checks the borrowed code this app depends on for publicly known security holes.

The gate is wired to the lanes

The deploy instructions are a file in the repository. These four lines are the ones that matter.

CODE 

deploy-frontend:
  name: Deploy frontend to GitHub Pages
  needs: checks
  runs-on: ubuntu-latest
PLAIN ENGLISH

"Here is the job that publishes the app people actually use."

A human-readable name, so a failure in the dashboard says something useful.

The whole point. This job does not start until every security lane has passed. One word — needs — is the difference between "we check our code" and "we cannot ship unchecked code".

And it runs on a fresh rented Linux machine, not on anybody's laptop. Same result every time, no "works on my machine".

⚠️
A gate has consequences

Wire the gate to the lanes and a lane failing for an unrelated reason — a newly published security advisory in borrowed code, say — will stop your deploy dead. That is the system working, not breaking. The fix is to clear the lane, not to unbolt the gate.

The meter that runs

Every AI review costs real money and takes real seconds. So the limit is checked before the call, not after.

CODE 

// Check the daily limit before calling Gemini. The unique constraint below
// is still the source of truth — it catches concurrent requests — but
// reaching it meant paying for and waiting on a generation we then threw
// away.
const alreadyGenerated = await this.prisma.aiFeedback.findFirst({
  where: { userId, generatedAt: { gte: todayStart, lte: todayEnd } },
  select: { id: true },
});
if (alreadyGenerated) throw this.rateLimited(todayEnd);
PLAIN ENGLISH

The comment explains a change, and why it was worth making: the check used to happen after the expensive part.

It also admits what this check is not — the database rule underneath is still the real referee, because two requests arriving at the same instant can both pass this check.

So this is an optimisation, not a guarantee. Saying that out loud stops a future reader from deleting the database rule as "redundant".

Look for any review this person already generated today…

…and only fetch the id. Pulling the whole review, text and all, to answer a yes/no question is wasted work on every single request.

If one exists, stop here — before a single token is spent — and tell the caller when they can try again.

💡
Key insight — cheap checks before expensive work

A database lookup costs a millisecond. An AI call costs money and seconds. Ordering them correctly is free. Any time you ask an AI assistant to add a paid API call, ask it the same question: what is the cheapest thing that could stop this call from being made at all?

What you can now do

Six modules ago, a tap on "save" was magic. Here is what it is instead.

1
You can locate a bug

Wrong number on screen → follow the data backwards. Nothing saves → check whether the server answered at all. Saved but invisible → a stale cache.

2
You can name what you want

"Validate at the boundary." "Make this write idempotent." "Invalidate the query after the mutation." "Rotate refresh tokens with reuse detection." Precise words get precise code.

3
You can catch a bad suggestion
